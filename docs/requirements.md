# 需求（草案 v0）

> 状态：讨论中。标「待定」的地方还没有答案，不要当成已定。

## 0. 定位

这不是「一个游戏」，是**一个世界模拟器 + 一个示例世界**。

玩家不是世界的中心，只是其中一个有身体、有位置、会受伤、会被记住的行动者。世界按自己的规则
运转，NPC 有自己的目标和知识边界，物品有材料与来源，配方有代价。

## 1. 目标与非目标

**目标**

- 一个可以被反复游玩、也可以被反复改造的世界。
- 系统是**数据**，内容是**可写的**，社区能造世界而不只是造 mod。
- 不接 LLM 也完整可玩；接上 LLM，世界会说话。

**非目标**

- 实时制。回合制是设计选择，也是 LLM 延迟的解药。
- 多人联机。
- 3D、物理、动作游戏手感。
- 商业化运营（打赏除外）。

## 2. 世界怎么跑

- **时间**：以「回合」为最小单位推进。一个回合 ≈ 几秒的世界时间。
- **持久化**：存档 = 局面快照 + 追加式事件日志。两者都要能过 schema 校验。
- **随机**：全局唯一 RNG，种子 + 存档可完全复现。
- **离线演化**：待定（见 §8-A）。

## 3. 基座：唯一必须先写的代码

所有系统都长在这四件事上。基座不稳，上面盖什么都会塌。

1. **实体-组件**：世界里的东西都是实体（id + 组件集合）。位置、身体、背包、知识都是组件。
2. **动作-效果**：所有「做一件事」都是动作：消耗资源 → 经过时间 → 产生效果列表。
3. **时间与事件**：回合推进、事件写入、事件触发的知识传播。
4. **世界包加载与校验**：读数据、验数据、拒绝坏数据。

## 4. 系统清单（归约表）

用户视角的「很多系统」，在实现上是**少数原语 + 大量数据**。这张表是本项目的核心判断：

| 系统 | 归约成 | 形态 |
|---|---|---|
| 实体系统 | 基座本身 | 代码 |
| 物品系统 | 实体 + 组件（材料 / 重量 / 耐久 / 标签） | 数据 |
| 技能系统 | 动作（AP + 资源 → 效果列表） | 数据 + 判定 |
| 采集 | 动作（工具 + 资源点 + 时间 → 产物） | 数据 |
| 制造 / 合成 | 配方（输入 + 时间 + 技能检定 → 输出） | 数据 |
| 战斗 | 动作 + 部位组件 + 回合队列 | 代码 + 数据 |
| 世界生成器 | 内容工厂，产出同一套数据 | 代码（AGPL） |
| 钩子 | 事件订阅 + 效果类型注册 | 数据 / 受限脚本 |

**结论**：采集、制造、合成不是三套系统，是同一个「配方/动作」模型的不同参数。引擎要写的代码
是基座；工程量大的是**内容**，而内容可以靠社区并行生产。

## 5. 内容生产

- 世界生成器：离线跑一次，产出能过校验的世界包。
- 钩子：优先做「数据级扩展」（新物品、新配方、新效果类型），脚本级扩展（Lua/WASM）后置。
- 分发：itch.io 项目页 + 仓库里的世界包索引 JSON。
- 教程：新手世界包（教玩家「采集 → 合成 → 用」的最小循环）。

## 6. 第一个可玩世界（微型世界）

不是为了好玩，是为了**证明基座**。每个系统只做一个实例：

- 1 间屋子、1 个 NPC、1 个可采集的资源点
- 2 个物品（1 个原料、1 个成品）
- 1 个配方（原料 + 时间 → 成品）
- 1 个技能（打某个部位）
- 1 场可以输的战斗 → 被俘 → 逃脱

一局 30 分钟，跑通「采集 → 合成 → 使用 → 冲突 → 失败 → 翻盘」。

## 7. 验收标准（待定）

候选：

- 玩家在没有引导的情况下，第一次就完成了「采集→合成→使用」。
- 玩家输了一次，但没有重开，而是继续玩下去。
- 玩家能说出某个 NPC「知道什么、不知道什么」。
- 另一个开发者能在不看代码的情况下，只改 JSON 就加进一件新物品和一个新配方。

## 8. 开放问题

- **A. 世界是否离线演化？** 玩家不在场时，NPC 和势力是否继续行动？这决定要不要一个「世界 tick」，
  是架构级分叉。
- **B. 玩家能改造世界到什么程度？** 只捡东西，还是能建造、种植、经营？这决定「持久化世界状态」
  的规模。
- **C. mod 能不能加系统？** 只能加内容（物品/配方/技能数据），还是能加新的规则类型？后者需要
  脚本层，是最大的架构分叉。
