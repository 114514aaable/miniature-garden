# 架构

本文只写**已经定下来的约束**和**待定的草案**。标了「草案」的部分可以推翻，标了「约束」的部分
不要绕。

## 1. 目标与非目标

**目标**：一个可离线、可确定性重放、可被社区扩展的方格回合制 RPG；LLM 只负责「说人话」和
「做选择」，不负责规则。

**非目标**：实时制、纯对话游戏、必须联网、必须用某个模型厂商。

## 2. 数据流

```
            （离线，一次性）                      （运行时，确定性）
  ┌──────────┐   ┌──────────┐   ┌────────┐   ┌────────┐   ┌──────────┐
  │ worldgen │ → │ validate │ → │ 世界包 │ → │ engine │ ↔ │ 玩家输入 │
  └──────────┘   └──────────┘   └────────┘   └────────┘   └──────────┘
                                    ↑              ↕
                                    └──────── lorekeeper（可选，独立进程）
```

- **worldgen**：AGPL CLI，产出一个世界包目录。可以跑一次，也可以跑一百次挑一个。
- **validate**：schema + 引用完整性。生成器的输出必须过这一关，过不了就是生成器的 bug。
- **engine**：MIT。读世界包，跑规则，出画面。**没有 LLM 也必须是完整游戏。**
- **lorekeeper**：AGPL 独立进程。引擎通过 localhost HTTP 或子进程问它「这个 NPC 现在该说什么」。
  它不存在时，引擎回落到 T0 脚本台词。

## 3. 三条边界（约束）

1. **生成时 / 运行时**：运行时不允许出现「让模型现编世界」的调用。模型只能读世界包里已有的
   知识条目，不能新增设定。新增设定必须走事件 → 存档 → 下次打开时仍是数据。
2. **进程边界 = 许可边界**：AGPL 代码（`tools/`）不得以库的形式进入引擎进程。通信只走
   文件、stdin/stdout、localhost HTTP。
3. **数据 / 代码**：世界包是数据。引擎不执行包内代码。脚本能力（如果有）必须沙箱化。

## 4. 回合模型（已定 v0）

**一个 tick = 一回合。** 动作有成本（整数回合），成本为 0 的动作不推进时钟。

- **时钟**：单调整数 tick，由 `store.step(n)` 推进。`(tick, seq)` 定序，零帧动作靠 seq 区分先后。
- **成本**：`costOf(动作, 速度)`，减到 0 就是零帧。速度是「减成本」，不是乘时间。
- **玩家**：输入驱动。一次动作花 cost，`playerReadyAt = tick + cost`。
- **敌人**：调度器驱动，见 4.1。
- **行动顺序**：`(readyAt, handle)`，不看数组顺序——刷怪顺序变化不影响复现。
- **不做**：行动点（AP）、反应点、同时宣言。它们和「成本即时间」这套是两种模型，不能混。

### 4.1 调度器

每个单位一个 `readyAt`（下次能行动的 tick）。每 tick 取最小的，平局按 handle。

- `take()` 先占位到 `tick + 1`，`done(cost)` 用真实成本覆盖；
- NPC 的零成本动作至少占 1 tick（否则同一 tick 无限行动）；
- 玩家**不在**调度器里，由输入驱动；
- `upcoming(n)` 只读，调试叠层和以后的行动顺序条共用它。

### 4.2 敌人 AI 与意图

**AI 只做选择，不做判定。** 它产出信封（`core.move` / `core.enemy_windup` / …），
判定仍由规则做——所以敌人和玩家走同一条求值路径、同一份日志。

**意图是数据**：`core.intent { tiles（相对敌人的偏移）, damage, resolveAt }`。

- 起手时写入，到点结算；
- **命中判定读它**，渲染（以后的红格）也读它——画的和打的永远同源；
- 玩家在 `resolveAt` 前离开那些格子就落空。

### 4.3 渲染管线

- 服务端只发**快照**（投影后的实体与地形），不发绘制指令；
- 浏览器 60fps：视觉位置每帧从逻辑位置重算（`visual.ts`），落后超预算直接瞬移，
  delta 用 `min(now-last, last-last2)` 钳制；
- `buildFrame` 是纯函数（快照 → 绘制指令），Canvas 只是执行器；
- 图集用 TexturePacker JSON hash（帧名 = 源路径），查不到帧退回字符。

### 4.4 日志

两种，读者不同：

- **开发日志**（已有）：完整、结构化、意图与落地分开，给排查用；
- **玩家日志**（未做）：取舍、人话、可合并，给叙事用。

不要合并成一套——一个怕漏，一个怕吵。

## 5. 部位模型（草案 v0）

六个部位：头、躯干、左臂、右臂、左腿、右腿。

| 字段 | 说明 |
|---|---|
| `hp` | 该部位独立血量，归零即失能 |
| `state` | `ok / hurt / crippled / disabled / restrained / missing` |
| `slots` | 装备槽（手部可持物） |
| `skills` | 绑在此部位的技能 id 列表 |

规则：

- **技能挂在部位上**。部位状态不满足条件时，技能置灰并给出原因（「右臂脱臼，无法劈砍」）。
- **技能带瞄准部位**。攻击可指定目标部位；不同部位有不同修正（腿难打但收益高）。
- **部位后果**：断腿 → 移动 AP 翻倍；断臂 → 双手技能不可用；头受伤 → 命中与视野下降；
  被束缚的部位 → 该部位技能全部不可用，且可被「利用」（拖拽、缴械）。
- **失能与死亡分离**：部位全失能 = 被制服，不是死亡。这给「求饶 / 被俘 / 谈判」留出空间。

待定：
- 是否需要连续的「疼痛 / 失血」计量，还是只保留离散状态？（离散更好读，连续更真实）
- 部位是否要分左右以外的更细粒度（手指、眼睛）？可能作为可选规则包。

## 6. 知识模型（草案 v0）

一条知识 = 一个可独立注入的陈述 + 可见性 + 归属。

**解析流程**（`lorekeeper` 或 T0 内置）：

```
候选集 = 公开条目
       ∪ 同 cluster 的条目
       ∪ 同势力条目
       ∪ holders 含此 NPC 的条目
       ∪ 事件揭示的条目
     ↓ 按 visibility 过滤
     ↓ 打分：相关度（关键词/图谱）+ 空间距离 + 时效
     ↓ 截断到该 NPC 的预算
```

**预算**由 `npc.tier` 决定：

| tier | 上下文预算 | 典型用途 |
|---|---|---|
| 0 | 0 tokens | 只用预生成台词 |
| 1 | ~1.5k | 本地小模型，闲聊与氛围 |
| 2 | ~6k | 云端模型，关键 NPC，剧情对话 |

待定：
- **传闻失真**：NPC 知道的是「错误版本」的知识，这需要条目支持 `variant_of` 与可信度。
  这可能是本作最有意思的机制之一，但要先想清楚它怎么被玩家发现。
- 知识是否会随时间过期（`decay`）？

## 7. 事件与知识增量

世界是静态生成的，但游戏过程会改变它。做法：

- 运行时写**追加式事件日志**：`{turn, actor, action, targets, witnesses, outcome}`。
- 事件 → 知识增量：目击者获得「亲历」版本；同势力/同区域的人获得「传闻」版本（可失真）；
  被封锁的事件不传播。
- 存档 = 快照（当前局面）+ 事件日志（可重放）。两者都要能过 schema 校验。

这是整个设计里最容易被低估的部分：不做这层，NPC 会集体失忆，或者全员全知。

## 8. AI 分级

| 级别 | 推理位置 | 延迟 | 成本 | 用在哪 |
|---|---|---|---|---|
| T0 | 无 | 0 | 0 | 杂兵、路人、所有无 LLM 场景 |
| T1 | 本地小模型 | 0.5–2s | 电费 | 队友、常驻商人、次级 NPC |
| T2 | 云端 | 1–4s | 按 token | Boss、关键知情者、同伴 |

LLM 的输出**只能是**：选一个合法动作 + 一句台词 + 一个情绪标签。引擎负责把动作翻译成规则调用。
模型永远不直接改数值。

## 9. 开放问题

这些还没有答案，欢迎在 issue 里吵：

1. 同时宣言 vs 顺序回合，哪个更适合「动态」？
2. 部位血量是离散还是连续？疼痛要不要做成资源？
3. 技能是「挂在部位上」还是「挂在武器上、由部位提供可用性」？
4. 传闻失真怎么让玩家**可感知**，而不是变成隐藏的随机噪声？
5. 世界包要不要一个 `events.json` 存放「开局前的历史」？
6. 多人同场（玩家 + 多个 LLM NPC）时，上下文预算怎么切？
7. 存档用快照还是纯事件溯源？纯事件溯源好看但重放成本高。
8. 角色卡（`content/`）与世界包（`worlds/`）的边界在哪？同一个 NPC 能不能被两个世界复用？

## 10. 预留与不做

这一节的作用是：让三年后的贡献者知道，某些东西不是「忘了做」，是**想过不做**。

留缝不留门：数据留位、注释写清配方、文档写清代价，但**不加没有实现的参数**。

| 预留什么 | 谁可能会加 | 加了会坏什么 | 现在的状态 |
|---|---|---|---|
| **第三维（z）** | 多层矿道、塔楼、桥 | 寻路、视野、生成、界面全要重写 | `strides` 留了位，实现没做 |
| **嵌套空间** | 城镇 / 大陆 / 星球缩放 | 跨层坐标、跨层寻路、跨层可见性 | `parent` 字段永远是 null |
| **场（温度 / 火 / 灵气）** | 需要连续物理或魔法扩散 | 新增一层 per-cell 数值矩阵与算子 | 未开始；注意它**不是**第四维 |
| **N 维张量** | 大概没人 | 通用引擎是无底洞，算法并不通用 | 不做 |
| **脚本层（Lua/WASM）** | mod 想加新机制 | 沙箱、预算、许可边界 | 不做，语言优先 |
| **管线（LLM）** | 接模型说话 | 延迟、成本、可重放 | 未开始，见 §8 |

两条判断标准：

1. **加维度 ≠ 加玩法。** 存储可以泛化，算法不能；玩家只能感知二维（加层）。
2. **通用是项目死掉的地方。** 需要的是「能跑、能查、能扩」的地图，不是数学库。

## 11. 已知限制与待办

- **键盘大小写**：现在只认小写（w/a/s/d/e/r）。做按键设置时改成存 event.code，一次解决。
- **规则文案未 i18n**：规则返回的中文原因（「够不着」「那里没有可以打的东西」）还没走语言包，等界面文案稳定后统一改。
- **界面文案**：静态标签已走 {{key}} + game/locales/zh-CN.json；动态文案还在页面里硬编码。

### 11.1 待办：把「开始游戏」做成独立的 UI 组

现在启动器里的东西是手写 DOM，还没用上自己的套件：

- **种子弹窗**（`openSeedDialog`）是手搓的：一个 fixed 遮罩 + input + 两个按钮；
- **读档面板 / 设置面板**是页面里直接拼的；
- 启动器页还是**经典脚本**，import 不了 `game/systems/ui`（游戏页是 module，启动器不是）。

要做的：

1. **启动器页改成 module**，让它能 import `game/systems/ui/spec.js` + `dom.js`；
2. 套件补两个控件：`input`（文本/数字）与 `field`（标签 + 控件一行）；
3. 种子弹窗、读档、设置改用 `modal` + 套件控件；
4. **「开始游戏」单独成一个 UI 组**：它本质是「初始化一个世界」——
   种子 + 以后的开局选项（难度、角色、出生点、包组合）都放这里，
   内容由世界包声明（`startMenu`），套件负责画。

原则：**页面里不再手写一次性的浮层**，凡是能重复出现的界面都走套件。
只此一处的例外是启动器本身的骨架（它要先跑起来才能加载套件）。
